# 河南科技学院入校登记系统（后端）SPEC文档

# 1. 文档概述

## 1.1 文档目的

本文档作为**河南科技学院入校登记系统（Entry Registration System, ERS）**的需求规格说明书（SPEC），明确系统的功能需求、非功能需求、接口规范、技术架构、数据规范等核心内容，为后端开发、前端开发、测试、运维等相关人员提供统一的开发、测试及部署依据。

系统基于**renren-fast开源框架**进行二次开发，采用**Spring Boot + MyBatis-Plus**技术栈，实现访客预约申请、审批管理、入校记录、数据可视化等核心业务流程。

## 1.2 文档范围

覆盖系统的全部核心模块：

**访客端模块**：用户注册/登录、个人信息管理、入校申请、数据看板、日历视图

**审批管理模块**：访客管理、申请审批、黑名单管理、批量操作

**系统管理模块**：统一认证、管理员管理、系统配置、监控统计

**数据管理模块**：入校记录、爽约记录、操作日志

# 2. 系统概述

## 2.1 系统背景

为解决河南科技学院访客入校管理混乱、登记流程繁琐、数据追溯困难、入校权限管控不严格等问题，开发入校登记系统，实现访客线上申请、管理员线上审批、入校扫码核销、数据可视化统计的全流程管理，提升校园入校管理效率与安全性。

## 2.2 系统目标

### 2.2.1 功能目标

- 实现访客、管理员的精细化管理，确保入校操作权限可管控、可追溯；
- 完成访客注册、入校申请、审批、核销、记录查询等全流程操作，支持数据导出；
- 提供入校统计分析功能，生成可视化报表，为管理决策提供数据支持；
- 支持系统配置灵活调整，适配校园入校管理场景变化；
- 实现系统日志记录、异常监控，保障系统稳定运行。

### 2.2.2 非功能目标

- 性能：接口响应时间≤500ms，并发量≥100QPS，支持至少500用户同时在线
- 安全性：支持密码加密存储、接口鉴权、防SQL注入、防XSS攻击，敏感数据加密传输；
- 可用性：系统可用性≥99.9%，支持故障快速恢复，关键数据定时备份；
- 可扩展性：架构设计支持模块横向扩展，接口设计支持版本迭代，便于后续功能升级；
- 可维护性：代码规范、文档完整，日志清晰，便于问题排查和系统维护。

## 2.3 系统边界

### 2.3.1 系统内部边界

明确系统包含的核心模块，以及各模块之间的划分的边界，例如：访客端 + 个人数据模块、审批核心 + 访客管理模块、统一认证 + 配置 + 监控模块、统计分析模块、系统配置模块、日志模块，各模块独立封装，通过接口进行数据交互。

### 2.3.2 系统外部边界

明确系统与外部系统的交互范围及限制，例如：

- 与校园门禁系统对接，获取入校核销数据；
- 向校园管理系统推送访客入校记录；
- 不涉及支付、物流等业务，相关功能由外部系统独立实现，本系统仅做数据关。

## 3.8 系统配置模块

### 3.8.1 功能描述

实现运行参数的灵活高效管理，可对爽约规则、入校时段、特殊日期等核心业务进行动态配置，且变更即时生效。

### 3.8.2 核心功能点

- **爽约配置查询**：从配置表查询爽约规则，解析JSON配置返回配置详情，包括迟到分钟数、爽约次数限制、黑名单天数等参数。
- **爽约配置修改**：支持修改爽约规则参数，包括迟到分钟数(0-120)、爽约次数限制(1-10)、黑名单天数(1-365或永久)，修改后即时生效并同步更新Redis缓存。
-  **时间配置查询**：查询入校时段规则配置，返回时段列表，每个时段包含开始时间、结束时间、最大人数、是否启用等属性。
- **时间配置修改**：支持修改入校时段配置，时段不能重叠，最大人数必须大于等于0，至少保留1个可用时段，修改后即时生效并同步更新Redis缓存。
- **特殊日期新增**：支持添加特殊日期配置，包括日期(yyyy-MM-dd)、类型(节假日/闭校日)、备注说明，节假日不影响预约，闭校日禁止预约该日期。
- **特殊日期查询**：查询特殊日期配置列表，支持按年份筛选，返回日期、类型、备注等信息。
- **特殊日期删除**：支持删除已存在的特殊日期配置。
- **定时任务-爽约检查**：每30分钟定时扫描，查询已过期未入校的记录，标记申请状态为已爽约，写入爽约记录表，检查是否触发黑名单。
- **定时任务-令牌清理**：每日凌晨执行，删除令牌黑名单表中已过期的Token，清理Redis过期缓存，保留最近7天记录用于审计。

# 5. 接口规范

## 5.1 接口整体规范

- 接口风格：采用RESTful风格，HTTP/HTTPS协议；
- 请求方式：GET（查询）、POST（新增）、PUT（修改）、DELETE（删除）；
-  请求/响应格式：JSON格式，编码为UTF-8；
- 接口地址：统一前缀为 /api/v1/，后续拼接模块路径（如 /api/v1/user 对应用户管理模块）；
- 鉴权方式：采用Token鉴权，请求头携带Token（Key：Authorization，Value：Bearer + 空格 + Token值）；
- 状态码：遵循HTTP标准状态码，结合业务场景补充自定义状态码（见5.2）；
- 参数命名：采用小驼峰命名法（如 userName、userId）；
- 日期格式：统一为 yyyy-MM-dd HH:mm:ss（如 2024-01-01 12:00:00）；
- 异常处理：接口异常时，返回统一的异常响应格式，包含状态码、错误信息、请求ID（便于排查）。

## 5.2 状态码规范

| 403        | Forbidden             | 无权限访问        |
| 404        | Not Found             | 资源不存在        |
| 500        | Internal Server Error | 服务器内部错误    |
| 10001      | 业务自定义            | 手机号已存在      |
| 10002      | 业务自定义            | 该时段名额已满    |
| 10003      | 业务自定义            | 访客在黑名单中    |

# 6. 数据规范

## 6.1 数据库设计规范  

- 数据库类型：MySQL 8.0及以上；

- 字符集：数据库、表、字段统一使用UTF-8字符集；

- 命名规范：


    - 数据库名：采用小写字母，下划线分隔，如 management_system；
    - 表名：采用小写字母，下划线分隔，前缀为模块缩写（如 user_ 代表用户模块），如 user_info、user_role；
    - 字段名：采用小写字母，下划线分隔，如 user_id、user_name；
    - 主键：每张表必须有主键，主键命名为 表名_主键字段（如 user_id），采用自增整数或UUID；_
    - _外键：外键命名为 表名_关联表主键字段（如 user_dept_id 关联 dept_info 的 dept_id），外键需设置关联删除/更新规则。

- 字段类型：根据数据长度和用途选择合适的字段类型，避免浪费空间，例如：

    - 用户ID、角色ID等标识类字段：int（自增）或 bigint；
    - 姓名、账号等字符串字段：varchar（长度根据实际需求设置，如 varchar(50)）；
    - 密码字段：varchar(128)（存储加密后的数据）；
    - 日期时间字段：datetime（如 create_time、update_time）；
    - 状态字段：tinyint（如 0-禁用，1-启用）。

- 索引：对常用查询字段（如 account、dept_id、role_id）建立索引，提升查询性能；避免过度索引，影响插入、修改效率。

## 6.3 数据校验规范

- 必填校验：所有必填字段（如账号、密码、部门ID）必须进行非空校验，缺失时返回明确的错误提示；


- 格式校验：
        
  
    - 手机号：符合手机号格式（11位数字，以13、14、15、17、18、19开头）；
    - 邮箱：符合邮箱格式（包含@、.等字符）；
    - 密码：长度≥8位，包含字母、数字、特殊字符；
    - 日期：符合 yyyy-MM-dd HH:mm:ss 格式。

- 唯一性校验：唯一字段（如登录账号、字典编码）必须进行唯一性校验，避免重复数据；
- 范围校验：状态、数量等字段需进行范围校验（如状态只能是0或1，数量不能为负数）；
- 关联校验：关联字段（如部门ID、角色ID）需校验是否存在于对应的数据表中，不存在时返回错误提示。

# 7. 技术架构

## 7.1 架构概述

本系统采用单体分层架构，基于 Spring Boot 搭建，分为前端交互层、Spring MVC 控制层、业务逻辑层、持久层与数据存储层，各层职责清晰、协同工作；部署阶段基于 Linux、Docker 与 Nginx 实现容器化交付与反向代理，确保系统的可维护性、稳定性与可扩展性。

## 7.2 技术栈选型  

| 架构层   | 技术选型                                        | 说明                                                         |
| -------- | ----------------------------------------------- | ------------------------------------------------------------ |
| 后端框架 | Spring、Spring Boot 2.x、Spring MVC             | 通过 Spring Boot 快速开发，简化配置、提升开发效率，适配单体架构 |
| 持久层   | MyBatis、MyBatis-Plus                           | 简化数据库操作，支持分页、条件查询等功能                     |
| 数据库   | MySQL 8.0                                       | 关系型数据库，稳定、高效，支持大数据量存储                   |
| 缓存     | Redis                                           | 缓存热点数据，提升系统性能，减少数据库压力                   |
| 日志     | Logback                                         | 日志收集、存储、分析，便于问题排查                           |
| 部署     | Docker、Docker、Nginx                           | 容器化部署，简化部署流程，支持横向扩展                       |
| 其他     | JWT（Token生成与校验）、MinIO（文件存储，可选） | 实现Token鉴权、文件上传下载等功能                            |

## 7.3 架构分层说明  

### 7.3.1 应用层

包含系统所有业务逻辑，按模块划分业务服务，例如：用户服务、权限服务、业务数据服务、统计服务等，各服务独立封装，通过接口交互。

### 7.3.2 持久层

负责与数据库交互，实现数据的增删改查操作，封装数据访问逻辑，隔离数据库细节，便于后续数据库迁移或替换。

### 7.3.3 网关层

统一接口入口，负责请求路由、鉴权、限流、日志记录等功能，拦截非法请求，保护后端服务安全。

### 7.3.4 数据层

包含数据库、缓存、文件存储等，负责数据的持久化存储和缓存，确保数据的安全性和可用性。

## 8.3 部署流程

1. 环境准备：部署服务器，安装所需软件（JDK、MySQL、Redis等），配置环境变量；

2. 数据库部署：创建数据库，执行初始化SQL脚本，配置数据库权限、连接池参数；

3. 缓存部署：配置Redis，设置密码、持久化方式，启动Redis服务；

4. 应用部署：将后端应用打包为Jar包（或Docker镜像），上传至应用服务器，配置应用参数（数据库连接、Redis连接等）；

5. 服务启动：启动后端应用，检查服务运行状态，确保接口可正常访问；

6. 测试验证：执行基础功能测试、接口测试，确认系统运行正常；

7. 监控配置：配置系统监控（如CPU、内存、接口响应时间），设置异常告警。

## 8.4 维护需求

- 日常维护：定期检查服务器运行状态、数据库状态、Redis状态，清理日志文件；
- 数据备份：每日定时备份数据库，每周进行一次备份恢复测试，确保备份有效；
- 版本更新：系统升级时，需先备份数据和应用程序，再进行更新，更新后进行测试验证；
